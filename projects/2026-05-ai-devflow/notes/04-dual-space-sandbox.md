# v4: 双空间 Sandbox 架构

> **触发问题**: 契约先行和产品探索期需求不稳定之间的矛盾怎么解?
> **结论信心度**: 中高 — 分阶段的思路正确,但 Sandbox 定位还不够清晰(长期仓库 → 腐化)
> **被下一版如何推翻**: v4 的 Sandbox 仍是"持久仓库",v6 会改成 Ephemeral(临时分叉,用完即焚)。v5 先独立处理 Brief 的问题。

## 关键洞察: 产品工作的两个阶段

| 阶段 | 目标 | 需求状态 | 工作性质 |
|---|---|---|---|
| **探索期（Divergent）** | 找到对的问题和对的解法 | 假设、模糊、频繁推翻 | 原型、试错、用户反馈 |
| **收敛期（Convergent）** | 把验证过的解法做扎实 | 稳定、可契约化 | 工程化、集成、上线 |

v3 设计的流程（契约先行 + 6 道 CI Gate）是**收敛期的流程**，直接套到探索期会产生强烈摩擦：
- 契约写了又改，改了又废
- CI 频繁挂掉，失去信号意义
- 产品陷入"先写契约"的仪式感，反而慢于用 Figma

**正确的架构不是一套流程，而是"两个互不干扰的工作空间 + 一道明确的迁移门"**。

## 双空间架构

```
┌─────────────────────────────────────────────────────────┐
│  Sandbox (探索期)                                         │
│  • 产品 own 全部代码                                       │
│  • 独立仓库 / monorepo 子目录 / 独立部署                    │
│  • 无契约要求、无 CI gate、无代码审查                      │
│  • 可用 AI 生成任意结构,包括假后端                          │
│  • 用真实用户 / 内部人员测试                                │
└────────────────────┬────────────────────────────────────┘
                     │ Promotion Gate
                     │ (通过验证的需求才迁移)
                     ▼
┌─────────────────────────────────────────────────────────┐
│  Production (收敛期) — 即 v3 的流程                       │
│  • 契约先行 + CODEOWNERS + 6 道 CI Gate                   │
│  • 产品、研发分工明确                                       │
│  • 面向正式用户,追求稳定和可维护                            │
└─────────────────────────────────────────────────────────┘
```

## Sandbox 的具体形态（v4 版本的思路）

**三种实现方式**（按组织规模选）：

- **方式 A：独立仓库 + 独立部署**（推荐用于小团队）
- **方式 B：monorepo 子目录 + 独立应用**
- **方式 C：纯前端 prototype 工具**（v0.dev、Bolt、Lovable）

**Sandbox 里没有契约，靠什么对齐？**

不是 OpenAPI，而是**数据契约草稿**——带注释的 TypeScript 类型。

**Sandbox 里的数据怎么办？**

| 方案 | 适用 | 风险 |
|---|---|---|
| 纯 mock 数据 | 交互原型 | 无数据持久性 |
| BaaS（Supabase / Firebase） | 需要真实后端行为 | 数据隔离靠配置 |
| 生产数据的只读脱敏副本 | 需要真实规模感 | 需运维支持 |

**禁止**：Sandbox 直连生产数据库。

## Promotion Gate: 从 Sandbox 到 Production

这是**整个架构的枢纽**。

### 触发条件

产品判断某个探索"成了"才发起 Promotion，标准应明确：
- [ ] 核心交互经过至少 N 个真实用户测试
- [ ] 关键指标达到预设阈值
- [ ] 产品内部已就"最终形态"达成一致
- [ ] 愿意承诺未来 3 个月不颠覆性推翻

### 流程要点

1. 产品提交 Promotion Brief（Sandbox URL + 核心交互录屏 + 数据草稿 types.ts + 已知边界 case）
2. 研发研读 Sandbox 代码，识别：哪些 UI 可复用 / 哪些逻辑需重写 / 需要什么 API / 数据模型怎么建
3. 研发输出 Promotion Plan：契约草案 / 数据模型 / PR 拆分 / 预计时间
4. 产品确认契约
5. 进入 v3 的 6 道 gate 流程

### 谁做 Promotion 的"翻译"？

**研发**。产品不需要学会写契约，不需要学会建数据模型。产品交付的是：
- **可运行的 Sandbox**（是什么）
- **用户反馈的证据**（为什么要做）
- **已知的边界 case 列表**（哪里复杂）

**核心规则**：Promotion 不是"代码迁移"，是**重新实现**。
- Sandbox 代码是一次性的，像建筑师的草图模型
- 生产代码基于从 Sandbox 学到的结论重新实现
- UI 组件**可能可以复用**（如果 Sandbox 用的是生产的 design system）
- 业务逻辑**通常要重写**（因为生产要考虑并发、错误、权限、测试）

## 对比：v3 vs v4 的效率

### v3（契约先行）

```
Day 1: 产品想到需求
Day 1-2: 产品 + 研发对齐契约 (来回改 3 次)
Day 3: 契约锁定, 开始开发
Day 5: 产品发现用户根本不想要这个功能 😱
Day 5: 契约作废
```

### v4（双空间）

```
Day 1:   产品在 Sandbox 用 AI 生成原型 v1
Day 1-2: 给 5 个用户试用, 收集反馈
Day 3:   AI 生成原型 v2 (简化了交互)
Day 4:   再测, 发现 mute hours 是多余的
Day 5:   产品决定: 只做 channel 选择, 发起 Promotion
Day 6:   研发 review Sandbox, 输出契约和计划
Day 7-9: 并行开发, CI 全程守护
Day 10:  灰度发布
```

关键差异：
- Day 1-5 完全没有研发介入
- Day 5 才产生契约,此时契约已经稳定
- 作废的原型不产生工程成本

## 架构的边界与风险

**什么时候不适用**：
- 强合规场景（金融、医疗）
- 深后端特性（分布式事务、大数据管道）
- 已有大量存量用户的成熟产品

**架构的已知风险**：
- Sandbox 成为"永久分支"，始终不 Promote → 自动过期
- 产品对 Sandbox 上瘾 → 公开指标，Promote 转化率
- Sandbox 代码被无脑复制到生产 → 流程里明确禁止
- 探索期 UX 结论在 Production 走样 → E2E 从 Sandbox 开始写

**组织前提**：
- 产品必须被授权"独立决定要不要做"
- 研发必须愿意做"翻译者"
- 领导层必须理解"Sandbox 代码会被丢弃"不是浪费

## 当时的小结

> **产品和研发的协作不是一套流程，而是两套空间 + 一个迁移门。**
> - **探索期**：产品在 Sandbox 用 AI 自由造，零契约、零 CI gate
> - **收敛期**：研发主导 Promotion，按契约 + 6 道 gate 并行交付
> - **Promotion Gate**：把 Sandbox 的探索成果翻译成生产契约，是两个空间的唯一通道

## 当时未解决的问题

两个问题被后续两版分别处理：

- **Brief 的质量问题**（v5 解决）：产品如果只给 Sandbox + 一份手写文档,研发的 AI 还是要重新"翻译",效率不够
- **Sandbox 的腐化问题**（v6 解决）：Sandbox 如果长期存在,会逐渐脱离生产实际,Brief 质量下降
