# v2: 全栈协作分工框架

> **触发问题**: 把视角从前端拉到全栈, 分工还成立吗?
> **结论信心度**: 中 — 提出了"AI 穿透能力"这个维度, 但流程仍是口头约定
> **被下一版如何推翻**: 这一版提出了"产品安全区"但没说怎么物理隔离。v3 用分支 + CI 把它变成可执行规则。

## 关键新洞察: AI 在代码栈不同层的"穿透能力"不均

| 层 | 典型工作 | AI 替代率 | 风险 | 人类判断的核心价值 |
|---|---|---|---|---|
| **UI / 交互** | 页面、组件、状态、路由 | 80%+ | 低 | 信息层级、节奏、交互心智模型 |
| **BFF / CRUD API** | 表单提交、列表查询、数据聚合 | 60–70% | 中 | 接口契约设计、错误语义 |
| **核心业务逻辑** | 计费、权限、状态机、工作流 | 30–40% | 高 | 领域建模、不变量、一致性 |
| **数据层 / Schema** | 表结构、索引、migration、事务 | <15% | 极高 | 演进策略、数据契约、范式权衡 |
| **性能 / 容量 / 可用性** | 缓存、队列、熔断、限流 | <10% | 极高 | 容量假设、失败模式、SLO |
| **Infra / SRE** | CI/CD、监控、告警、发布 | 20–30% | 高 | 发布策略、可观测性设计 |

**核心观察**：AI 从"上层（靠近用户）"向"下层（靠近系统）"穿透能力递减。越往下越需要研发把关；越往上越可以让非研发角色用 AI 直接产出代码。

## 产品能力边界的扩张与陷阱

**产品 + AI 现在能产出的**：
- 可点击的 UI 原型（真实组件，非 Figma）
- Mock API（MSW / json-server / Supabase 直接跑）
- 接口契约（OpenAPI / TypeScript types）
- 数据结构草案
- 用户路径的 E2E 测试用例
- 简单的业务规则代码

**产品即使有 AI 也不该独立交付的**：
- 任何涉及**并发**的逻辑（锁、事务、幂等）
- 任何涉及**钱和权限**的关键路径
- 任何**需要演进**的数据模型
- 任何**跨服务**的一致性保证

**边界的三条判断规则**：
1. **一次性 vs 长期维护**：用完就扔的 demo 随便写；长期维护必须研发接管
2. **前台 vs 后台**：展示逻辑产品可写；状态改变（写入）需要研发审查
3. **本地 vs 跨系统**：单服务内可容忍；跨服务/跨团队必须走契约流程

## 三种典型的全栈协作模式

### 模式 A：垂直切片模式（VM0 文章的样子）

```
产品/设计 → UI Shell + Mock Data   ← 产品用 AI 完整产出
                    ↓ "注入灵魂"
研发       → API + Auth + DB + Infra ← 研发把 mock 换真实
```

适用：UI 密集型产品、重构、新应用冷启动

### 模式 B：水平分层模式（小团队/创业）

```
产品 + AI：完整 MVP（前端+业务+mock DB）  ← 产品 own 业务垂直面
         ↓
研发：平台层（Auth / 多租户 / 消息队列 / 监控）← 研发 own 共享基础设施
```

适用：产品能力强的小团队、内部工具、多条业务线并行

### 模式 C：Spec-as-Code 模式（大团队/高一致性要求）

```
产品 → 用 AI 把 PRD 编译成: OpenAPI 契约 / TS 类型 / E2E 用例 / 验收标准
研发 → 按契约实现前后端, CI 自动验证
```

适用：大团队、金融/医疗等合规场景、多端一致

## 全栈实现时的关键工程问题

这一版识别出五个**必须由研发掌控**的硬骨头：

1. **Schema 所有权** — Schema PR 必须研发批准
2. **接口契约的双向锁** — 契约文件作为单一事实源
3. **"能跑"到"能扛"的差距** — 研发的新核心职责是把产品跑通的切片"加固"到生产级
4. **技术债的可见性** — 代码分区 + 定期 review + Feature flag
5. **测试策略的重新分工**:
   - E2E（用户路径）← 产品
   - 集成测试（API 契约）← 研发
   - 单元测试（核心逻辑）← 研发
   - 性能 / 压测 ← 研发
   - 可视化回归（UI）← 产品

## 研发角色的重构

**研发不是被替代，而是被"上移"。** 新四大职能：

1. **Platform Builder** — 建组件库、API 脚手架、数据层抽象
2. **Contract Designer** — 定义前后端、服务间的接口契约
3. **Quality Gatekeeper** — 守住可维护性和性能底线
4. **Delivery Strategist** — Feature flag、灰度、监控、回滚

## 当时的小结

> **不是"产品取代研发"，也不是"产品辅助研发"，而是协作接口从"文档/口头"升级为"可运行代码"。**
>
> 产品的能力边界向下扩张到 UI 和 mock 层；研发的能力重心向上提升到平台、契约、质量门禁。两者的中间地带——**业务逻辑、数据契约、发布策略**——成为真正需要 co-design 的新阵地。
